v1.8 把平板版的存储迁移到可移除的内存卡上，并把并发度从 4 首提升到 32 首。更重要的是，这个版本记录了一次完整的端到端性能排查：瓶颈最终并不在应用之内，而在设备的无线链路上。修正链路后，实测吞吐从约 5 MB/s 提升到 67 MB/s。

存储方面，应用从 `getExternalFilesDirs()` 返回的目录中，选取可移除且已挂载的卷作为缓存根目录。这是系统为每个应用分配的专属目录，无需申请任何存储权限。我们特意把视频数据（`SimpleCache`）和离线清单索引放在同一个根目录下，让二者始终同生共灭：如果内存卡临时未插好，应用会回退到内部存储并开启一套独立的缓存，而不会因为「索引存在、数据缺失」把卡上完好的内容误判为损坏并清除。首次迁移时，内部存储中的旧缓存会通过 `SimpleCache.delete()` 连同其数据库记录一起清理，随后在卡上重新下载。

并发方面，我们先在电脑上对视频中转服务器做了短时并发测试：8 条连接 20.3 MB/s，16 条 33 MB/s，32 条 41.5 MB/s，吞吐随连接数近似线性增长，说明服务端仍有余量。据此，平板版的 worker 数提升到 32 个，每首歌的音视频各占一条连接，最多 64 条；各 worker 以 300 毫秒间隔错峰启动，避免瞬时冲击。

在这一过程中，我们发现了一个隐藏很深的瓶颈：OkHttp 在服务端支持 HTTP/2 时，会把发往同一主机的所有请求复用到**一条** TCP 连接上。对普通 API 调用而言这是优化，但对大文件并行下载来说，它意味着无论开多少并发，所有数据都挤在同一个 TCP 拥塞窗口里，并行实际上被抵消了。为此，下载专用客户端被强制限定为 HTTP/1.1，连接池扩大到 64，确保每个分片请求都拥有独立的 TCP 连接。

然而，完成上述改动后，设备实测吞吐依然只有约 5 MB/s，并发提升几乎没有带来收益。我们随即按链路逐段排查。存储端：在内存卡上用 `dd` 顺序写入 300 MB，速度为 53 MB/s，排除存储瓶颈。服务端：在电脑上以 32 条连接持续下载 30 秒，稳定在 58.2 MB/s，排除服务端瓶颈。应用端：统计设备上处于 ESTABLISHED 状态的 TCP 连接，共 76 条，证明并发确实生效。最后检查无线链路，发现平板连接在 2.4 GHz 频段，协商为 WiFi 4（802.11n），链路速率仅 144 Mbps，扣除协议开销后的有效吞吐正好落在 5～10 MB/s 区间，与观测值吻合。

在我们的环境里，平板的上游是一台通过有线接入千兆网络的电脑所开的热点，链路瓶颈就出在这台热点上。将其切换到 5 GHz 的 36 信道后，平板协商为 WiFi 5，但链路速率只升到 192 Mbps——热点默认只用了 20 MHz 频宽。再把信道宽度设为 80 MHz，链路速率达到 866 Mbps。此时平板实测下载吞吐为 67 MB/s，70 秒内完成 167 首，缓存在几分钟内增长到 7.9 GB。对于遇到类似问题的用户，我们的建议是：先确认设备是否工作在 2.4 GHz 频段，这往往是最便宜、也最有效的提速手段。

这个版本也暴露出一个严重的副作用。32 个 worker 在每首歌开始时都要向 Invidious 主服务器请求一次播放清单，短时间内产生了数百次请求，导致我们的出口 IP 被一个公共实例封禁。该问题的分析与修复见 v1.9。
