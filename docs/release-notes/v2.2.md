v2.2 让平板版接入了一个自建的私有 Invidious 服务器，并在家长设置中加入了服务器测速与自动择优。在把私有服务器真正跑通的过程中，我们依次定位并修复了四个问题：网络层不可达、故障转移误判、应用层自我限流，以及字幕匹配策略过窄。修复完成后，平板实测下载吞吐达到 58 MB/s，字幕覆盖率从 15% 提升到 33%。

自建服务器的决定是前两个版本的自然结论：公共实例不可依赖，直连 YouTube 又会被 PO Token 校验挡住。官方的 `invidious-companion` 组件恰好解决了后者——它内置了 BotGuard 挑战的求解能力，可以自行生成 PO Token。我们在家里为平板提供热点的那台电脑上部署了完整的服务栈：`invidious` 提供歌单、清单与字幕接口，`invidious-companion` 负责与 YouTube 交互并中转媒体流，`postgres:14` 作为 Invidious 的数据库。三个容器运行在同一个 podman pod 中，通过 quadlet 交由 systemd 管理，设置为开机自启、异常自动重启；同时启用了 `podman-auto-update` 定时器，每天检查一次镜像更新——YouTube 的接口变化频繁，companion 需要及时跟进。服务端口只绑定在热点网卡的地址上，只有连入该热点的设备能够访问，有线网络和公网都无法触及。部署后的首次验证令人振奋：companion 的日志显示「Successfully generated PO token」；在 v2.1 中被 yt-dlp 判定为不可播放的那首儿歌，在这里返回了包含 11 条媒体流的完整清单；频道歌单的响应时间为 0.8 秒；单条连接的媒体下载速度为 11 MB/s。

平板版随之把私有服务器设为默认数据源，原公共实例保留在列表中作为备用。由于家庭内网中的私有服务器通常不配置 TLS，应用的网络安全配置也相应放开了明文 HTTP。家长设置的服务器面板新增了测速功能：先调用频道信息接口测量响应时延，再取一首已存歌曲的播放清单，以 Range 请求下载其 H.264 视频流的前 4 MB 测量实际吞吐，全程只产生 3 次请求。「全部测速，选最快的」会串行地测试列表中的每台服务器——刻意避免并发测试给服务器带来突发压力——然后自动切换到吞吐最高的那一台。

第一个问题出现在网络层。新版本安装后，下载速度为零，平板端提示无法连接服务器。服务端容器运行正常，从平板 ping 电脑也完全通畅，问题显然不在链路层。进一步检查防火墙规则后发现，NetworkManager 在开启热点时，会把热点网卡归入 firewalld 的 `nm-shared` 区域，而该区域的入站规则只放行 DHCP（67/udp）、DNS（53）、SSH（22/tcp）和 ICMP，其余端口一律拒绝。我们只在这一区域放行了服务所需的 3000/tcp 与 8282/tcp 两个端口，没有影响其他网络区域。

第二个问题出在故障转移逻辑。放行端口、重启应用后，速度依然为零。日志中有一条看似自相矛盾的记录：应用以「私有服务器出问题」为由，切换到了公共实例，而括号中的原始报错却是「无法连接公共实例」。顺着这条线索分析，我们还原了事件顺序：应用启动时，持久化的当前服务器仍是上一次故障转移留下的公共实例；它在切回私有服务器的瞬间，仍有一批发往公共实例的请求在途，这些请求失败后报告的错误，被归咎到了刚刚切换过去的私有服务器，触发了又一次错误的切换。修复方式是让故障转移在惩罚一台服务器之前，先核对错误信息中出现的主机名：如果报错明确指向列表中的另一台服务器，就视为过期信号直接忽略。

第三个问题是性能。修复前两个问题后，下载恢复了，但吞吐只有约 8 MB/s，远低于私有服务器的能力。服务端日志给出了答案：每分钟只处理约 30 次清单请求，而且字幕补全的请求在同一个队列中交替排队。我们单独测量了清单接口：首次请求耗时 0.3～0.5 秒，命中服务端缓存后仅需 0.01 秒，服务器本身并不慢。真正的瓶颈是应用自己：v1.9 为保护公共实例设计的串行闸门（单许可、700 毫秒间隔），被原样施加在了自建服务器上，32 个 worker 大部分时间都在排队等清单。由于私有服务器只为我们自己服务，我们为它单独设置了一个允许 8 个并发、不设间隔的闸门，公共实例继续使用原来的严格策略。调整后，平板实测吞吐稳定在 58 MB/s。

第四个问题关于字幕。端到端验证时我们注意到，已检查的 295 首歌曲中只有 44 首获得了字幕，其余 251 首被标记为「无字幕」，比例明显异常。随机抽查被标记的歌曲后发现，其中一首实际带有简体中文字幕，另一首带有英文自动字幕——问题出在匹配策略上：v2.0 只接受与频道语言一致的字幕，一个英文频道的视频即使附带了高质量的中文字幕，也会被判定为没有字幕。新的策略引入了语言优先级：频道语言最优先，其次是中文，最后是英文；同一语言内，人工字幕优先于自动生成的字幕。为了让历史数据也受益于新策略，我们为字幕规则增加了版本号，规则升级时会一次性清除所有「无字幕」标记，让后台协程重新查询。调整后，已检查的 303 首中有 101 首获得字幕，覆盖率约为 33%；抽查剩余的歌曲，确实没有任何可用字幕，这在儿歌类视频中相当普遍。

最后，我们在真机上做了完整的回归验证：中文分类正常加载，宝宝巴士的歌曲播放流畅，「字」按钮能即时开关字幕。截至验证时，设备已离线存储 1017 首、共 23 GB。

目前仍有两个已知限制。其一，少数视频只能通过 YouTube 的备用客户端（`TV_SIMPLY`）获取，这种情况下 H.264 编码最高只有 480p，更高清晰度只提供 AV1 编码，而多数平板缺少 AV1 硬件解码能力，这些歌曲因此会以 480p 存储。其二，私有服务器依赖家中的电脑在线；但这并不影响离家使用，因为那时平板只播放已经存好的内容。
